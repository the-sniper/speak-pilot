# Speak Pilot

Describe a team in one sentence. Get a grounded, evidence-cited English training program —
placement, curriculum, weekly progress, and manager-facing drafts — generated by an LLM and
checked against real human-annotated speech data at every step that can be checked.

Built as a take-home / interview pilot for Speak, in the style Speak itself builds in:
scaffolded and driven by a coding agent (Claude Code), with the commit history left intact
rather than squashed into one shot.

---

## What it is

Speak Pilot takes one line from an L&D manager — "18 people on our Seoul support team, escalation
calls in English, 10 weeks" — and turns it into a full program:

1. **Placement.** Every learner in the seeded cohort is placed into a band (A1–C1) by an LLM
   reading real per-learner pronunciation evidence, with a mandatory citation back to at least
   one real utterance id. The evidence panel plays the actual audio, shows word- and
   phoneme-level agreement across five human expert raters, and lets a manager override the
   model's band next to it — never over it.
2. **Curriculum.** Weekly themes, role-specific scenarios, a cadence, plain-language success
   criteria, and a bilingual kickoff message, streamed section by section over SSE as it's
   generated.
3. **Weekly pass.** An "Advance" step computes that week's facts in code (completion,
   score movement, at-risk) from seeded session data, then asks the model for judgment only —
   a manager brief and any outreach drafts — never arithmetic.
4. **Drafts, never sends.** Every outreach message an "Advance" produces lands as
   `status: "draft"`. A human edits or approves it; nothing in this codebase sends anything,
   anywhere, ever.
5. **Evals.** A 20-brief sweep (Appendix B of the build guide — clear, vague, constrained, and
   deliberately adversarial briefs) drives every LLM call through the same code path production
   uses, and scores the result: schema conformance, placement accuracy against real expert
   consensus, latency, cost, and scenario relevance judged by an LLM and checked against a
   second, independently-formed LLM label (an inter-model agreement rate, not human validation —
   see [Eval numbers](#eval-numbers) below).

## The honesty line

> Northwind Support and its people are fictional. Every recording, score, and expert annotation
> is real human-annotated learner speech from speechocean762 (CC BY 4.0). The week-over-week
> trajectory is constructed — the dataset captures one session per speaker, so progress over time
> is simulated by ordering real utterances. Placement accuracy is measured against real expert
> consensus and is not simulated.

This exact text is the banner (`src/components/HonestyBanner.tsx`) rendered on every screen in
the app, not just here. A few things it doesn't spell out, stated plainly:

- **The cohort of 24 speakers was curated**, not randomly sampled — `scripts/select-cohort.ts`
  deliberately seeds at least one speaker per band so the demo spans A1 through C1 instead of
  showing 24 near-identical cards. The five-band cutoff table it's graded against
  (`src/lib/bands.ts`) is untouched by that curation — see [Eval numbers](#eval-numbers).
- **The band table was fixed and published before any eval sweep ran.** It is derived once from
  the corpus-wide five-expert mean accuracy distribution and never tuned against a result.
- **The week-over-week trajectory on the program page and in the QBR is constructed, not
  measured.** speechocean762 has no repeat-session data — each speaker recorded once. An
  "improving," "plateaued," or "declining" arc is a narrative device built by ordering that one
  real session's utterances by score, not a trend observed over calendar time. Every figure this
  touches carries an inline `simulated` tag at the point of the claim, not only in this banner.
- **The QBR's "Print / save as PDF" button is `window.print()`.** That is the entire export
  path — there is no PDF-generation library, no headless-browser render, no server-side
  rendering pipeline. The browser's own print dialog (and that dialog's own "Save as PDF"
  destination) produces the file.
- Both the eval sweep's LLM judge *and* the comparison labels in `docs/eval-human-labels.ts`
  (despite that file's name — see its header) were written by an LLM (this build's coding agent),
  not a person — see [Judge vs. labeler agreement](#judge-vs-labeler-agreement). That is an
  honest limitation of this pilot's scope, not a hidden one.

## How to run locally

Prerequisites: Node 20+, a local Postgres (Docker Compose config is included, or point
`DATABASE_URL` at any Postgres instance), ffmpeg (audio conversion at seed time), and the
speechocean762 dataset downloaded to `../.speak-pilot-data/speechocean762/` (outside this repo;
see the build guide, Step 1).

```bash
cp .env.example .env        # fill in DATABASE_URL and, optionally, LLM_API_KEY
npm install
npm run db:push             # drizzle-kit push — creates the schema
npm run seed                # builds the fictional org from real speechocean762 speech
npm run dev
```

Open `http://localhost:3000`, describe a team (or click the "Seoul support team" example chip),
and watch a program generate.

**Running with no API key at all — `.llm-cache/` is a committed replay corpus.** Every LLM call
this codebase makes is content-addressed and cached to `.llm-cache/*.json` on first real call
(see `src/lib/llm/cache.ts`); that directory is committed to the repo, unlike `.env`, specifically
so the app can run with zero API spend:

```bash
LLM_PROVIDER=openai LLM_API_KEY= REPLAY=1 npm run dev
```

### Replay verification

Under `REPLAY=1`, a cache miss throws `CacheMissInReplayError` instead of silently falling
through to a live provider call — checked against the running app, not just asserted:

- **Positive.** With `LLM_API_KEY` genuinely absent from the process (no `.env` present at all,
  every other env var set explicitly) and `REPLAY=1`, submitting the Seoul brief through the UI
  streamed a complete program — cohort, 24 placements, all 10 curriculum weeks, cadence, success
  criteria, bilingual kickoff — in **10.0 seconds** server-side (`POST /api/programs/generate 200
  in 10.0s`, from the dev server's own log). The three `agent_runs` rows this write produced all
  show `provider: openai`, `cache_hit: true`, `latency_ms: 0` — every byte came from
  `.llm-cache/`, nothing reached the network.
- **Negative.** Submitting a brief guaranteed not to be in the cache (novel text, never run
  before) under the same `REPLAY=1` failed **immediately** (16ms, not the 5–170 seconds a real
  `gpt-5` call takes) with `CacheMissInReplayError` surfaced straight to the screen: "REPLAY=1 but
  no cached response for `<hash>`. Run once with a real provider first." — not a silent fallback
  to a live call, and no crash from the missing key either, because the cache check happens
  before the provider is ever reached.

```bash
npm test           # vitest — see Verification below for the current count
npm run evals       # the 20-brief sweep against whatever LLM_PROVIDER is set
```

## Eval numbers

Real numbers from one real sweep: `scripts/run-evals.ts` against `LLM_PROVIDER=openai`,
`LLM_MODEL=gpt-5`, all 20 briefs in `docs/eval-briefs.ts` (Appendix B), sweep id
`bdc8dd00-e60d-422d-b213-a728865eea1e`. See the live, always-current version at `/evals`, which
reads directly from `agent_runs` and shows exactly one sweep's numbers, never a pool across
every sweep ever run.

**Placed 478 of 480 learner-placements within one band of expert consensus (99.6%); exact-band
match 58.8%.** Both numbers, same prominence — with five bands, ±1 is a generous metric on its
own, and quoting only the flattering one is exactly what this project's honesty standard rules
out. Ground truth is `learners.trueBand`, computed once at seed time from the five-expert mean
accuracy and never touched by any model; n = 480 because every one of the 24 seeded learners is
re-placed by all 20 briefs (24 × 20 = 480).

**1 of 20 briefs (5%) did not complete.** Brief 9 ("Make our Tokyo office more comfortable on
client calls") failed on a genuine network/transport error partway through its curriculum call —
not a schema violation, and not the model refusing or misbehaving. This surfaced a real gap:
`callWithSchema` (`src/lib/llm/adapter.ts`) used to let a transport error (as opposed to a
response that arrived but failed schema validation) escape before ever writing an `agent_runs`
row, so the failure log the Evals tab renders was blind to it — `scripts/run-evals.ts` printed
"every attempt was written to agent_runs," and for this failure class that claim was false. Fixed
during this same task: a transport error is now caught and logged (`ok: false`, the transport
error's message, `output: null`) exactly like any other failure, with a regression test
(`src/lib/llm/adapter.test.ts`). The historical sweep above predates that fix, so its own
`agent_runs` rows for brief 9 stop after `cohort` and `placement` with no `curriculum` row and no
failure-log entry — `/evals`' "Incomplete briefs" section (and `src/lib/evals.ts`'s
`incompleteBriefs`, a generic check, not hardcoded to brief 9) is what makes that gap visible
instead of silently invisible.

**Schema conformance: 100% valid on first try, 78 attempts, 0 retries needed** — across every
brief that did reach a schema-checked call. This number does not include brief 9's transport
failure (a transport error is a different failure class from a schema violation, and — per the
gap above — this specific sweep predates that failure class being logged as a row at all).

**Live vs. cache-served: 52 of 78 calls were real (live) OpenAI calls; 26 were served from
`.llm-cache/`** (an earlier, interrupted attempt at this same sweep had already fetched real
responses for some briefs — re-running reused them rather than re-paying for them, all real
responses, none fabricated). Latency and cost below are computed **only over the 52 live calls** —
a cache hit is genuinely instantaneous and free, not fast, and pooling it into a percentile would
silently understate real latency.

**Real latency is minutes per generation against `gpt-5`, not seconds** — this is exactly why
`REPLAY=1` over a prebuilt cache (see [Replay verification](#replay-verification)) is what makes
the demo viable at all; the build guide's "12-20 seconds total" pacing figure describes the mock
provider, not a live reasoning-model call:

| step | live calls | avg | max |
|---|---|---|---|
| cohort | 6 | 13.2s | 17.3s |
| placement | 16 | 76.8s | 100.7s |
| curriculum | 15 | 98.6s | 168.3s |
| judge | 15 | 9.0s | 13.0s |

Per-step counts are thin (6–16 live samples each) — read these as representative samples of a
reasoning model's real latency on this task, not as a stable, statistically confident percentile.
Pooled across all 52 live calls (mixing fundamentally different call types together, which is
why the per-step table above is the more honest number to read): p50 66.3s, p95 118.4s.

**Cost is unmeasured.** `src/lib/llm/providers/openai.ts`'s `OPENAI_MODEL_RATES` is deliberately
empty — this project has not verified `gpt-5`'s published $/token rate against an authoritative
source, and guessing one would be worse than reporting "unknown." Every one of the 52 live calls
above has `cost: null` (a real call happened, price genuinely unknown) — never `$0.00`, which
would read as a measurement it isn't. The 26 cache-served calls report `cost: 0` correctly (no
API call happened at all — genuinely free, not the same claim as "unmeasured").

### Judge vs. labeler agreement: 68.4% (13 of 19 briefs)

The LLM judge scored every single judged brief 3 out of 3 — zero variance across all 19 scenarios
it saw (brief 9 never reached the judge step). That is itself worth flagging: a judge with no
discriminating power between "adequate" and "excellent" is a weaker signal than one that spreads
its scores, independent of whatever its agreement rate with a second labeler turns out to be.

**Both the judge and the "human" labels it's checked against in `docs/eval-human-labels.ts` were
produced by a language model** — this build's coding agent, reading each brief's real generated
scenario (pulled directly from `agent_runs` for the sweep above) and scoring it independently
against the Appendix A rubric, in writing, *before* querying or viewing the judge's own scores
(see that file's header for the exact procedure, including the SQL used, and the ordering). This
is an **inter-model agreement rate, not independent human validation**, and must not be read as
one. Labels from this repo's actual author, reading the real generated scenario text themselves,
would be a meaningfully stronger check and are the natural next step before trusting this number
for anything beyond "the harness plumbing works end to end."

## Architecture: what production would need

These are stated as decisions this pilot deliberately did not build, not as gaps discovered
after the fact:

- **Real auth.** There is no login, no session, no per-org isolation anywhere in this codebase —
  every route trusts every request. Production needs real authentication and authorization
  (who can see which cohort, who can approve a draft, who can override a placement) before any
  of this touches a real customer's data.
- **A production scheduler in place of the "Advance" button.** `AdvanceButton` calls
  `POST /api/programs/[id]/advance` — the exact route a real deployment would call
  automatically. Production needs a per-cohort weekly trigger (cron, queue consumer, or workflow
  scheduler) invoking that same route on the cohort's cadence, plus idempotency / a lock on
  `(programId, weekNumber)` so a retried or duplicate trigger can't double-advance a week, plus
  alerting on a failed advance (the route already returns 502 on a model/schema failure and 400
  on an out-of-horizon advance, so a missed week is detectable, not silent — it just isn't
  wired to page anyone yet).
- **Speak Level as the placement signal, in place of the public dataset.** Placement here reads
  speechocean762 — a public, English-read-aloud pronunciation corpus, chosen because it is real,
  human-annotated, and free to use. A production pilot for an actual Speak customer would place
  learners from Speak's own assessment (Speak Level), not a public academic dataset standing in
  for it.
- **Channel integration for drafts.** `DraftCard` supports exactly two mutations — save an edit,
  mark approved — and there is no "Send" affordance anywhere in this codebase, by construction.
  Production needs a real email/Slack integration behind the approve action, with its own
  audit trail, before an approved draft can actually reach a learner.
